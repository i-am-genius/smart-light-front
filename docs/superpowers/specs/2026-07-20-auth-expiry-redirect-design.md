# 登录失效跳转修复设计

## 问题

失效或缺失 JWT 经过后端 `JwtAuthenticationFilter` 后仍以匿名请求继续执行。后端没有配置 `AuthenticationEntryPoint`，Spring Security 最终返回空响应体的 HTTP 403。前端只在 HTTP 401 时清理登录态并跳转登录页，因此页面停留在受保护路由，WebSocket 同时持续用旧 token 重连。

前端登录成功时还只清理另一存储中的 `storeSetup`，没有清理旧的 `TOKEN` 和 `USER_INFO`。当用户切换“记住登录”选项时，旧 `localStorage` token 可能覆盖新写入 `sessionStorage` 的 token。

## 方案比较

### 方案 A：只在前端把所有 403 当成登录失效

改动最小，但会把“已登录但权限不足”错误地处理成退出登录，破坏 HTTP 403 的标准语义。不采用。

### 方案 B：只在后端把匿名访问改为 401

能修复本次跳转问题，但无法消除双存储中旧 token 覆盖新 token 的根因。不完整。

### 方案 C：修正后端状态码契约并清理前端冲突登录态

后端未认证统一返回 401，已认证但无权限继续返回 403；前端保持只对 401 执行退出，并在登录成功时清理另一存储中的旧认证数据。采用此方案。

## 后端设计

在 `SecurityConfig` 中配置统一的认证失败入口：

- 未携带、无效或过期的普通用户 JWT 返回 HTTP 401。
- 响应使用 JSON，业务码为 401，并给出“登录已失效，请重新登录”一类稳定消息。
- 已认证但权限不足仍由访问拒绝处理器返回 HTTP 403。
- REST 和 `/ws` 握手共用安全过滤链，因此在进入业务控制器或 WebSocket 握手拦截器前获得一致的 401 语义。
- `/ops-admin/**` 保持现有独立鉴权过滤器和响应行为。

## 前端设计

- Axios 收到 HTTP 401 时继续使用现有统一逻辑：清理两个存储中的认证和店铺状态，然后跳转 `/login`。
- 不把普通 HTTP 403 解释为登录失效。
- 登录成功后，在写入选定存储前，删除另一存储中的 `TOKEN`、`USER_INFO` 和 `storeSetup`，保证认证来源唯一。
- WebSocket 握手失败本身仍只会产生浏览器通用 `error` 事件；页面初始化 REST 请求收到 401 后跳转并卸载页面，从而停止重连。

## 测试

后端安全回归测试覆盖：

- 受保护 REST 接口无 token 返回 401 JSON。
- 受保护 REST 接口携带无效 token 返回 401 JSON。
- `/ws` 无 token 或无效 token 在安全过滤链返回 401。
- 已认证但权限不足仍返回 403（适用于存在角色限制的路径）。

前端回归测试覆盖：

- 切换到 `sessionStorage` 登录时清除旧 `localStorage` 认证数据。
- 切换到 `localStorage` 登录时清除旧 `sessionStorage` 认证数据。
- 401 继续清理登录态并触发登录页跳转；403 不触发强制退出。

## 范围

本次不修改 JWT 有效期、WebSocket 消息协议、设备端 `/ws/device` 鉴权方式，也不重构路由或全局状态管理。
